# Signing, notarisation and distribution

Three different situations, with different requirements. They are kept separate
here because mixing them up is the usual source of confusion.

## 1. Building and running it yourself

This is what `./scripts/build-release.sh` does by default, and what happens when
you press Run in Xcode.

- `CODE_SIGN_IDENTITY` is `-`, an **ad hoc** signature.
- No Apple Developer account is needed.
- The app runs on the Mac that built it.
- The build log will say *"Disabling hardened runtime with ad-hoc
  codesigning"* — that is expected; the hardened runtime setting only takes
  effect with a real identity.

One consequence worth knowing: an ad hoc signature changes on every rebuild, and
macOS ties privacy permissions to the signature. So macOS may ask again for
Screen & System Audio Recording after you rebuild. That is TCC working
correctly, not a bug in Snaplet.

An ad hoc signed app copied to another Mac will be refused by Gatekeeper. That
is the correct behaviour and Snaplet's documentation will never ask anyone to
disable Gatekeeper, run `spctl --master-disable`, or strip quarantine
attributes system-wide.

## 1b. Keeping permissions across rebuilds

Worth knowing before you spend an afternoon confused: macOS binds Screen &
System Audio Recording to the app's **code signature**, not to its path or
bundle identifier alone. An ad hoc signature is derived from the binary, so it
changes on every build — and every build therefore looks like a different app to
TCC. The symptom is unmistakable:

- System Settings still lists Snaplet with its switch on.
- Snaplet still says it needs the permission.
- `CGPreflightScreenCaptureAccess()` returns `false`.

Nothing is broken; the stored grant simply no longer matches the binary.

You have three options.

**Grant it again after each build.** Fine for an occasional build. Turn Snaplet
off and on again in System Settings › Privacy & Security › Screen & System Audio
Recording, then quit and reopen Snaplet. macOS reads this permission when the
process starts, so reopening matters.

**Reset the entry** when the stale one gets in the way:

```bash
tccutil reset ScreenCapture app.snaplet.Snaplet
```

This clears Snaplet's screen-recording decision so the next launch asks cleanly.
It changes your privacy settings, so run it yourself and only for this app.

**Sign with a stable self-signed certificate** (recommended while developing).
The grant then binds to the certificate rather than to the binary's hash, and it
survives every rebuild.

Create the certificate once, in Keychain Access:
*Keychain Access › Certificate Assistant › Create a Certificate…*, name it
`Snaplet Dev`, identity type **Self Signed Root**, certificate type **Code
Signing**. Then build with it:

```bash
SIGN_IDENTITY="Snaplet Dev" ./scripts/build-release.sh
```

Grant the permission once to that build and it stays granted. This certificate
is only good on your own Mac — it is not a substitute for a Developer ID, and it
does not let anyone else run the app.

## 2. Signing with a Developer ID

Needed before the app can run on someone else's Mac.

Requirements:

- A paid **Apple Developer Program** membership.
- A **Developer ID Application** certificate in your login keychain.
- Your 10-character Team ID.

```bash
# Confirm the certificate is present.
security find-identity -v -p codesigning

SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
DEVELOPMENT_TEAM="TEAMID" \
./scripts/build-release.sh
```

With a real identity the hardened runtime is applied, together with the
entitlements in `Snaplet/Resources/Snaplet.entitlements`:

- `com.apple.security.device.audio-input` — microphone recording
- `com.apple.security.device.camera` — the webcam overlay

Screen recording needs no entitlement; it is granted by the user through TCC.

Verify:

```bash
codesign --verify --deep --strict --verbose=2 dist/Snaplet.app
codesign --display --entitlements - dist/Snaplet.app
```

## 3. Notarising for distribution

Gatekeeper will still block a signed-but-not-notarised app downloaded from the
internet. Notarisation is a separate step performed by Apple.

You need credentials that Apple issues to you:

- An **app-specific password** for your Apple ID, or an **App Store Connect API
  key** (`.p8` file, key ID and issuer ID).
- Your Team ID.

None of these can be generated by this project, and none are stored in the
repository. If you set up notarisation in CI they must be repository secrets.

Store the credentials once:

```bash
xcrun notarytool store-credentials snaplet-notary \
  --apple-id "you@example.com" \
  --team-id "TEAMID" \
  --password "app-specific-password"
```

Then, after a Developer ID build:

```bash
xcrun notarytool submit dist/Snaplet-0.1.0-1.zip \
  --keychain-profile snaplet-notary --wait

# Staple the ticket to the app, then repackage so the zip contains it.
xcrun stapler staple dist/Snaplet.app
ditto -c -k --sequesterRsrc --keepParent dist/Snaplet.app dist/Snaplet-notarized.zip

# Confirm Gatekeeper accepts it.
spctl --assess --type execute --verbose=4 dist/Snaplet.app
xcrun stapler validate dist/Snaplet.app
```

## What CI does and does not do

The GitHub Actions workflow builds, tests and produces an **ad hoc signed**
`.app` artifact. It does not sign with a Developer ID and does not notarise,
because those need secrets that must not be exposed to pull requests from
forks. Adding them is a deliberate repository-owner decision:

- `DEVELOPER_ID_CERTIFICATE` (base64 `.p12`) and its password
- `DEVELOPMENT_TEAM`
- Notary credentials (app-specific password or API key)

## App Store

Snaplet is not built for the Mac App Store. It runs **without** the App Sandbox,
which keeps writing to any output folder you choose straightforward and avoids
security-scoped bookmarks. Shipping on the App Store would require enabling the
sandbox and reworking file access. That is not on the roadmap.
